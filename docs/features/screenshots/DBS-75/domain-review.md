| 1 | should-fix | §2 Token, §3 `session/redis.tf` | Within one apply the two values do match. Across applies they can drift apart. Both `*_wo_version` are a fixed `1`, and the ephemeral `random_password` gets a new value on every run. So when only one of the two resources is created or replaced, it gets a new token and the other keeps the old one. Three ways this happens: (a) the replication group fails or is tainted after the secret version was written; on re-apply the RG is created with token T2 while the secret still holds T1. (b) The secret write fails after the RG exists. (c) A force-new change on the RG (`subnet_group_name`, `kms_key_id`, at-rest settings, `-replace`). In each case the app or probe gets `WRONGPASS` and Terraform shows no diff. The claim "`apply` lại trong cùng phiên không đổi token" only holds for in-place updates. | doc §2 Token bullets 2 and 4; §3 diagram (both "version 1"); write-only semantics: the value is sent only when `*_wo_version` changes | Tie the two together. Add `lifecycle { replace_triggered_by = [aws_elasticache_replication_group.main.id] }` on `aws_secretsmanager_secret_version.redis_auth` (check in the spike that it also fires on a create after a failed create). Drive both `*_wo_version` from one variable or local (`redis_auth_version`), so a mismatch is fixed by bumping it once with `ROTATE`. Write the recovery steps in README and add a tf test that both versions come from the same source. |
