| 1 | blocking | R2/R3 (F-1) | The described `serializeMetadata` flow — "serialize trước (`JSON.stringify`), validate trên kết quả serialize" reusing one string for both validate+SQL — breaks on the single most common input, omitted `metadata`. `JSON.stringify(undefined)` returns the **JS value `undefined`** (not a string), and `JSON.parse(undefined)` throws `SyntaxError` before the guard logic ever runs. The *current* code avoids this only because it calls `JSON.stringify(input.metadata ?? {})` — the design's R2 text never says `serializeMetadata` defaults to `{}` before stringifying, and R2's own line "Giá trị đã `JSON.parse(JSON.stringify(x))`... không đổi hành vi hiện có" reasons about `x` directly, missing that `x = undefined` produces `undefined`, not a JSON string. Current code: `backend/src/modules/audit/audit.service.ts:30` (`JSON.stringify(input.metadata ?? {})`). Design text: `docs/features/DBS-56-audit-service-record.md` R2 §"F-1" and R3 §"F-1" (`serializeMetadata`), plus R4 TC-56-04c/TC-56-16 which assume the omitted case still passes. | State explicitly in R2/R3 that `serializeMetadata` defaults internally (`metadata ?? {}`) *before* `JSON.stringify`, exactly mirroring today's `audit.service.ts:30`, and add this exact case as its own assertion in TC-56-16 (not just implied by "mọi case accept hiện có của TC-56-07d") so a reviewer can see the omitted-metadata path was deliberately preserved, not missed. |
| 2 | should-fix | R2 (F-2) | The design's own TC-56-21 and the §R2 "fire-and-forget … ngoài phạm vi" caveat are in tension with a real call site already in the codebase: `AuditService.recordDenied` has no production caller yet, but `TransactionService.run` is used elsewhere (e.g. `identity.service.ts:72`) with the exact "nested async helper, awaited" shape TC-56-21 tests — i.e. the ALS *correctly* flags synchronous awaited nesting, which is good, but the doc doesn't acknowledge that a more subtle real-world case (a caller that `void`s an audit call from inside a `.then()`/event-emitter callback registered during the transaction, e.g. an outbox-consumer-style hook) escapes detection entirely and would show `getStore() === undefined` even *during* the still-open transaction's lifetime if that callback itself got invoked asynchronously but detached from the AsyncLocalStorage chain (e.g. via `setImmediate`/`EventEmitter.emit` triggered by unrelated code, not a chained `.then()`). This isn't new behavior introduced by the fix, but the doc's "không phải lỗi mới do fix này gây ra" undersells that this specific escape hatch is exactly where a future `OutboxWriter`-style producer (mentioned in `module-notes.md` "Async, events và audit") is most likely to accidentally call `recordDenied()` unprotected, with no runtime signal. | Verified empirically: an `EventEmitter` listener registered inside `als.run(true, fn)` and fired later from *outside* any ALS context reports `getStore() === undefined` when checked from the emitting (unrelated) call site, but `=== true` from inside the listener itself when invoked synchronously in the same microtask chain as `emit()` — behavior is inconsistent depending on exactly how the "detached" call is wired, which the doc doesn't explore beyond the single `.then()`/`void` example. | Add one sentence to R2 flagging this as a known, accepted gap specifically for future event/outbox-driven audit callers (not just generic "fire-and-forget"), so the next dev who wires `recordDenied()` into an async consumer doesn't assume the ALS guard is a universal safety net. |
