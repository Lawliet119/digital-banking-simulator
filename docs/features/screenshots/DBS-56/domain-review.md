| 1 | blocking | §3 (Interface dùng: `EntityManager.insert()`), TC-56-01 | `manager.insert(AuditLogEntity, …)` is a TypeORM InsertQueryBuilder. On Postgres it appends `RETURNING` for generated and default columns (`id`, `occurred_at`, `metadata`). `RETURNING` needs SELECT privilege on those columns. The documented target grant for `dbs_worker` on `audit_log` is INSERT only. Once the roles task lands, every worker audit write (risk flags) would fail with "permission denied", and in the worker that fails the whole transaction. TC-56-01 mocks `insert`. The db-specs run as table owner or superuser. Neither can detect this. | database-design §8 role matrix (`audit_log` api `S I`, worker `I`); `audit/README.md` ("`dbs_worker` chỉ có quyền INSERT"); `test/db/append-only.db-spec.ts` already shows the `SET LOCAL ROLE` pattern for a non-owner role. | Use a hand-written `INSERT INTO audit_log (…) VALUES ($1…$8)` through `manager.query`, with no RETURNING. | 2 | blocking | §2.4, §3 `AuditMetadata`, TC-56-07 | DoD #4 is not enforced. The compile-time check only rejects fresh object literals with an extra key. A variable or spread such as `const m = {id, email}` compiles. So does an `as` cast. A DTO, or a row read from the DB, passes unchecked. `id` and `reason` are plain `string`, so `reason: user.email` compiles. `action`, `role`, `target.type` and `target.id` are also free `string`s, with no check at all. database-design §4.2 and AC-11.3 put the lock/unlock *reason* in `audit_log`, so an operator's free text could land there (a name in a reason, for example). §2.4 says "no runtime whitelist because callers are internal", yet the table has no schema-level filter either. TC-56-07 only proves the literal case. | database-design §4.7 ("schema không tự lọc PII"; "Role/action/target_type vẫn là text mở"); database-design §4.2 (lock reason lives in `audit_log`); `common/errors/reject-reason.ts` and `ErrorCode` already exist as closed code sets. | Type `reason` as a closed set (`ErrorCode`/`RejectReason` or a new reason-code enum), `role` as the identity `Role` union, and `action` as a registry of string literals (`transfer.create`, `account.lock`, `access.denied`, …). Add a cheap runtime guard in `record()`: only keys `id|reason|count`; `id` is a uuid; `reason` matches `/^[A-Z0-9_.]{1,64}$/`; `count` is an integer. Reject NUL characters (`\u0000` in jsonb/text raises a Postgres error and would roll back the business transaction). Add TC-56-07b for the non-literal case (variable, spread, cast) and runtime tests for each rejected shape. |
| 3 | blocking | §2.3, §3 diagram case 3, TC-56-06, M-56-03 | TC-56-06 does not prove DoD #3. It commits a standalone `run()`, then throws. It would pass if DENIED were written in the same transaction as the business work, and even with no outer transaction at all. There is no negative control (throw inside `run` makes the row disappear) and no case where the outer business transaction exists and rolls back. DoD #3 asks for a stated mechanism *and* a test. The mechanism is only a caller convention. `AuditService` offers nothing that forces its own transaction, so ledger, accounts and risk will each hand-roll it. Hazards of the nested form are not stated. If DENIED is recorded inside a `run` callback, a deadlock retry duplicates it. The callback also holds one pooled connection while the DENIED transaction needs a second: with `DATABASE_POOL_MAX` (default 10) concurrent denials, every request holds one connection and waits for another. The DENIED insert also takes a FOR KEY SHARE lock on the `users` row, which can block on an outer transaction that is updating that row (for example `sessions_revoked_at` on lock). It is also not stated what happens if the DENIED write itself fails (500 instead of 404 is a visible difference, and the rule should be explicit). | docs/03 §6 sequence ("404, ghi nhật ký truy cập bị từ chối (transaction riêng)", and the ownership check comes *before* `BEGIN`); module-notes ("denial is audited DENIED in its own transaction"); `transaction.helper.ts` (retry re-runs `fn`; pool via `DATABASE_POOL_MAX`); `config/validation.schema.ts` (default 10). | Add a helper such as `AuditService.recordDenied(input)` that calls `TransactionService.run` itself, and document the rule "call it after or outside the business transaction, never inside a `run` callback". State what happens if the DENIED write fails. Tests: (a) an outer tx with a business write and a DENIED record in a separate tx, outer rolls back, the DENIED row survives and the business write is gone; (b) a negative control showing a DENIED written and then thrown inside the same `run` is lost; (c) a concurrent case with N > pool-size denials while an outer tx is open, or an explicit statement that the helper is only valid before BEGIN. Cite AC-5.8 / T11 in the trace. |
| 4 | should-fix | §2.2, §3, TC-56-03, TC-56-05, M-56-02 | The fail-closed claim "Kết quả: …kể cả các write khác" is proven only against a second *audit* row. It should use a write in a different table (the real shape: ledger / outbox / users row). The caller can also break fail-closed. TC-56-03 only re-tests `withTransaction` rollback with a stubbed insert, which `transaction.helper.spec.ts` already covers. The doc does not forbid catching. | `transaction.helper.ts` (commit after `fn`, no state check); module-notes ("never catch a DB error inside the callback (25P02)"). | Add to §2.2 and the module README: "never catch the `record()` rejection". Add a case where the callback swallows the error and show what `run()` returns, so the hazard is documented with evidence. Make TC-56-03 assert the error is the same instance and that `record` was reached through the real `run`. |
