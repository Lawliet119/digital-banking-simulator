| 1 | blocking | §1 Q2, §2 T3, §5 M-185-11 | The timing plan ignores ALB draining. `api` is a service task behind a target group with `deregistration_delay = 30`. On `stop-task`, ECS puts the task in DEACTIVATING, deregisters it, and waits for draining before it sends SIGTERM. The hung request keeps the connection open, so draining lasts the full 30 s. SIGTERM arrives about 30 s after `stop-task` and SIGKILL 2 s later. The request started its lock wait before `stop-task`, so its `lock_timeout` of 30 s (the Joi maximum) always fires first. The transaction then rolls back by timeout and the client gets the app's 503 through the draining ALB. Setting `stopTimeout=2` does not change this, so the run never interrupts a live transaction. | `infra/terraform/envs/dev/session/alb.tf` (`deregistration_delay = 30`), `ecs.tf` (`load_balancer` block on `aws_ecs_service.api`), `backend/src/config/validation.schema.ts:129` (`max(30_000)`) | Before M-185-10, set the target group's `deregistration_delay.timeout_seconds` to 0 with `aws elbv2 modify-target-group-attributes`, and list it as temporary drift that `destroy` removes. Log `stoppingAt` and `stoppedAt` from `describe-tasks`, and require `stoppedAt` < (send time of K + 30 s − margin). |

| 4 | should-fix | §2 diagram ("phát hiện client chết"), §2 ca biên, T4 | The orphan backend's behaviour is described wrongly. While it waits for a lock it does not read its socket. With `client_connection_check_interval` at its default of 0 it never notices the dead client, and TCP keepalive (hours) does not apply here. It ends in one of two ways. (a) `lock_timeout` 30 s after the wait began: ERROR, rollback, then FATAL when it writes to the closed socket. (b) The hold releases first: the orphan gets both row locks, sends the rows, then hits EOF or RST on its next read and aborts; at worst `idle_in_transaction_session_timeout` of 10 s ends it. It can never COMMIT, because COMMIT has to come from the client.
