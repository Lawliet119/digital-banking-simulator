### What I checked and found sound
- **Envelope:** caller envelope keys are removed in a new object, and the caller's object is not changed. Mixin skips keys that are already bound. Each key appears once on the root logger, the request logger and the filter line (TC-42-13/14 green, raw lines counted). `message` is always a string. Extra arguments with no placeholder are dropped.
- **`SafeLogger`:** catches failures, writes the fallback line at the same level and then swallows a second failure; keeps `this`. nestjs-pino `Logger.call` runs `Object.assign` and `instanceof` before the hook, so top-level getters and revoked Proxies are caught only by `SafeLogger`, as the design says.
- **`formatters.log` / hook guards:** a stream that throws on the pino-http `finish` listener does not become `uncaughtException` (probe `probe2.ts`: status 200, 2 writes attempted, no uncaught).
- **`safeErrorMetadata`:** never throws (revoked Proxy, throwing getters); allowlist for bare codes and network codes matches §2.
- **`ConfigValidationError.invalidKeys`:** can only hold schema key names or `&lt;cross-field&gt;`, never a value. The message is unchanged for existing callers. `main.ts` logs only metadata plus key names.
- **`http-logging.ts`:** resolves the id before `runInContext` and binds a UUID or `null`. Handler, completion and header carry the same id without the middleware (TC-42-05).
- **`main.ts` and the crash handlers:** import order is env, then the logging bootstrap, then bigint, then the dynamic `AppModule` import, pinned by `main-wiring.spec.ts`. Crash output on api and worker is one `level:60` line, exit code 1, nothing on stderr. Exit code 1 matches Node's default crash code, so behaviour is unchanged.
- **Money path:** `transaction.service.ts` has no diff in range, so retry and transaction boundaries are untouched. The filter change only touches log calls; HTTP contract and 500/503 mapping are unchanged (error-handling e2e green). `process.exit` is used only in the crash handlers.
- **Tests and PostgreSQL:** the new tests would fail on the old code where it applies (TC-42-05, 08, 11, 13, 14). None of the in-scope tests needs PostgreSQL; the crash e2e uses the preload and fires before any DB connection.
- **Out of scope:** `backend/README.md` §8 is not updated in this range, which is plan step 10, still to come.
